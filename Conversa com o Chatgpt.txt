Precisamos primeiro entender como o Google Drive entrega o áudio ao navegador e quais limitações existem para reprodução contínua/segundo plano.

Consultei a documentação atual do Google Drive e do navegador. A conclusão é boa para o DriveTune, mas há uma decisão arquitetural importante.

1. O Google Drive permite o que precisamos

A API do Google Drive permite obter o conteúdo de um arquivo binário, como MP3, através de:

GET /drive/v3/files/{fileId}?alt=media

e a documentação atual também confirma suporte a download parcial usando o cabeçalho HTTP Range. Isso é importante porque permite trabalhar com partes do arquivo em vez de necessariamente baixar o MP3 inteiro de uma vez.

Portanto, conceitualmente:

                    GOOGLE DRIVE
                         │
                    arquivo.mp3
                         │
                    Drive API
                         │
                         ▼
                  dados de áudio
                         │
                         ▼
                  HTML <audio>
                         │
                         ▼
                     CELULAR

é tecnicamente viável.

2. Mas eu mudaria uma coisa na arquitetura anterior

Eu não colocaria inicialmente um servidor nosso no meio do áudio.

A primeira arquitetura que eu testaria seria:

┌──────────────────────────────┐

│                              │

│  └───────────┬────────────┘  │
│              │               │

│              ▼               │
│       Google Drive API       │
└──────────────┬───────────────┘
               │

               ▼

3. Existe uma questão importante: o token OAuth

Aqui está a parte que merece atenção.

A chamada da API de conteúdo precisa de autorização. A documentação do Google deixa claro que o download do conteúdo exige um escopo que permita leitura do conteúdo; drive.readonly, por exemplo, permite visualizar e baixar os arquivos.

Portanto, o navegador precisará fazer algo equivalente a:

GET https://www.googleapis.com/drive/v3/files/ID_DO_MP3?alt=media
Authorization: Bearer ACCESS_TOKEN

Isso é perfeitamente compatível com a ideia do aplicativo.

4. E existe uma alternativa ainda mais interessante

O Google também disponibiliza o campo:

webContentLink

para arquivos que podem ser baixados pelo usuário.

Então precisamos testar experimentalmente duas estratégias:

Estratégia A — API diretamente
<audio>
   ↓
fetch / Drive API
   ↓
Authorization: Bearer ...
   ↓
Google Drive
Estratégia B — webContentLink
<audio>
   ↓
webContentLink
   ↓
Google Drive

Eu não escolheria definitivamente entre A e B apenas pela documentação.

Vamos fazer um pequeno protótipo.

5. O ponto mais importante: reprodução em segundo plano

Aqui a situação também é favorável.

A Media Session API permite que uma aplicação web forneça informações da música e registre ações como:

play
pause
nexttrack
previoustrack
seekbackward
seekforward

Esses controles podem ser apresentados pelo sistema operacional, inclusive em interfaces de bloqueio/notificação, quando o navegador suporta o recurso.

Portanto:

             CELULAR BLOQUEADO
                    │
                    ▼
        ┌──────────────────────┐
        │   Depeche Mode       │
        │   Enjoy the Silence  │
        │                      │
        │   ◀   ▶❚❚   ▶       │
        └──────────┬───────────┘
                   │
                   ▼
              DriveTune
                   │
                   ▼
             Google Drive

é um objetivo razoável.

Mas não devemos escrever no SPEC que isso é garantido em todos os celulares.

A própria documentação da MDN classifica Media Session como de disponibilidade limitada.

Então o requisito correto é:

O DriveTune deverá suportar reprodução em segundo plano e controles de mídia nos navegadores/dispositivos que ofereçam suporte às APIs necessárias.

6. Há uma descoberta importante para nosso projeto

O escopo:

drive.file

é mais restrito: permite acesso somente aos arquivos específicos que o aplicativo utiliza.

Já:

drive.readonly

permite visualizar e baixar todos os arquivos do Drive.

Como queremos que o usuário escolha uma pasta existente contendo sua coleção de MP3, isso precisa ser analisado com cuidado.

Eu não colocaria simplesmente drive.readonly no projeto ainda.

Queremos obter o menor escopo possível, porque isso influencia inclusive o processo de aprovação/verificação do aplicativo pelo Google.
